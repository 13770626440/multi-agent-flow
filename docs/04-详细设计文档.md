## 核心架构设计 (MVP-02-T02 及后续基础)

### 1. 通用任务模板 YAML Schema (完整版)

```yaml
template_id: "universal-task-flow"
version: "1.0.0"
description: "通用任务流程模板"

# 1. 全局输入定义 (实例化时必填)
input_schema:
  data_source: 
    type: string
    required: true
    description: "数据源 URL 或文件路径"
  report_format: 
    type: string
    default: "markdown"
    description: "报告输出格式"

# 2. 任务节点定义
tasks:
  - task_id: "step-1-data-collection"
    name: "数据收集与清洗"
    type: fixed # fixed / dynamic / review
    
    # 前置依赖 (DAG 控制)
    dependencies: []
    
    # 角色与能力要求
    target_role: "data-engineer"
    required_capabilities: ["web_scraping", "data_cleaning"]
    required_skills: ["scraper-tool", "pandas-expert"] # 声明所需 Skill
    
    # 执行上下文 (映射为 OpenMOSS 的 description)
    execution_context:
      instruction: "请从指定数据源抓取数据，清洗无效值，并输出为 JSON 格式。"
      input_mapping:
        source: "${input.data_source}" # 引用全局输入
      output_format: "json"
    
    # 输出定义
    output_definition:
      type: "file"
      format: "json"
      path: "/workspace/step-1/output.json" # 写入共享卷路径

    # 验收标准
    acceptance_criteria:
      - "输出合法的 JSON 数据"
      - "数据条目数大于 100"
    
    # 执行控制
    control:
      timeout: 300 # 秒
      retry_policy:
        max_retries: 2
```

### 2. Backend 调度循环 (Scheduler Loop) 逻辑

Backend 启动后台定时任务（每 5 秒），执行以下逻辑：

1.  **加载快照**：从数据库读取当前运行中任务的 DAG 快照。
2.  **轮询状态**：
    *   遍历所有状态为 `DISPATCHED` 的任务 ID。
    *   调用 OpenMOSS API `GET /api/sub-tasks/{id}` 获取最新状态。
3.  **状态处理**：
    *   **Case: `done`**
        *   获取产出路径 (`output_path`)。
        *   **解锁后续**：查找依赖该任务的所有后续任务。
        *   **依赖检查**：若后续任务的所有前置任务均 `done`，则将其状态更新为 `READY`。
        *   **数据注入**：解析后续任务的 `input_mapping`，替换变量为实际路径。
        *   **派发**：调用 OpenMOSS API 创建后续任务。
    *   **Case: `review` (评审通过)**
        *   同 `done` 逻辑，解锁后续。
    *   **Case: `review_failed` (评审驳回)**
        *   **创建修正任务**：生成新任务 ID（如 `step-1-fix`），依赖原任务，Description 包含驳回意见。
        *   将修正任务加入 DAG。
    *   **Case: `failed`**
        *   标记整个任务流失败，发送告警。
4.  **超时检查**：
    *   检查 `DISPATCHED` 任务的运行时间，若超过 `timeout`，调用 OpenMOSS API 终止任务并标记失败。

### 3. `agency-agent` Skill 工作流

所有 Agent 容器预装 `agency-agent`，其 `SKILL.md` 定义如下工作流：

1.  **接收任务**：Agent 从 OpenMOSS 领取任务，读取 `description`（包含 YAML 片段）。
2.  **解析需求**：
    *   提取 `required_skills` 列表。
    *   提取 `execution_context` 中的指令。
3.  **激活技能**：
    *   检查自身已加载的 Skills。
    *   若缺少所需 Skill，尝试从 `/skills` 目录加载（利用 OpenClaw 热重载）。
    *   在 System Prompt 中引入所需 Skill 的上下文。
4.  **执行任务**：
    *   读取 `input_mapping` 指定的文件路径（从 `/workspace` 读取）。
    *   执行指令。
5.  **提交结果**：
    *   将产出物写入 `output_definition` 指定的路径。
    *   调用 OpenMOSS API 提交任务。
