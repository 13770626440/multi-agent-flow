## 4. 代码质量审查

### 4.1 错误处理

| 模块 | 评估 | 问题 |
|:---|:---:|:---|
| **TemplateLoader** | ⚠️ | `load_template` 捕获了 `yaml.YAMLError`、`ValueError`、`Exception`，但 Redis 写入失败时只记录日志返回 False，没有通知调用方具体原因 |
| **AgentProvisioner** | ✅ | 每个步骤（创建 Agent、发送入职包、配置 Cron）都有独立的 try-except，错误处理完善 |
| **OpenClawClient** | ✅ | CLI 执行失败时返回 `{"status": "error", "error": ...}` 结构，不会抛出异常 |
| **OpenMOSSClient** | ⚠️ | `_request` 使用 `response.raise_for_status()` 抛出异常，但 `get_prompt` 和 `get_tool_cli` 静默返回空字符串/默认值，可能掩盖问题 |
| **Dispatcher** | ✅ | Push 失败自动降级为 Pull，有完善的 fallback 机制 |
| **SyncEngine** | ✅ | 单个子任务同步失败不影响其他任务，错误隔离良好 |
| **Decomposer** | ✅ | 自定义异常类型（JSONParseError、SchemaValidationError 等），错误分类清晰 |

### 4.2 日志记录

| 模块 | 评估 | 问题 |
|:---|:---:|:---|
| **TemplateLoader** | ✅ | 加载成功/失败、Agent 供给调度/完成/失败均有日志 |
| **AgentProvisioner** | ✅ | 每个关键步骤都有 info/error 级别日志 |
| **OpenClawClient** | ✅ | CLI 执行、成功/失败均有日志 |
| **OpenMOSSClient** | ⚠️ | `get_prompt` 使用 `logger.warning` 但返回默认 prompt，可能误导（Agent 使用的是通用 prompt 而非角色专属 prompt） |
| **Dispatcher** | ✅ | Push/Pull 状态切换均有日志 |
| **SyncEngine** | ✅ | 状态变更、解锁任务均有详细日志 |

### 4.3 边界情况

| 编号 | 场景 | 风险 | 处理情况 |
|:---|:---|:---:|:---|
| **B-001** | Redis 不可用时加载模板 | 高 | `load_template` 中 Redis 写入失败返回 False，模板不会进入缓存，但文件已存在。重启后需重新加载 |
| **B-002** | Watchdog 在 Docker 9p 文件系统上的事件丢失 | 中 | 使用 `PollingObserver(timeout=1.0)` 轮询模式，已适配 Docker 环境 |
| **B-003** | `run_coroutine_threadsafe` 在事件循环未启动时调用 | 中 | `template_loader.py` 第 178-180 行检查 `_event_loop`，为 None 时跳过并记录 warning |
| **B-004** | `importlib` 动态导入 `loader.py` 失败 | 高 | `agent_provisioner.py`、`decomposer.py`、`sub_task_creator.py` 均在模块加载时执行导入，如果文件不存在会直接 `raise FileNotFoundError`，导致整个应用无法启动 |
| **B-005** | DAG 快照中 `task_id` 与子任务 `id` 不匹配 | 中 | `sync_engine.py` 第 147 行使用 `completed_task.id in dependencies` 比较，但 DAG 快照中使用 `task_id` 字段，两者可能不一致 |
| **B-006** | `complete_sub_task` API 中 instruction 字段被追加消息 | 高 | `tasks.py` 第 295 行 `sub_task.instruction = sub_task.instruction + f"\n\n[Completion Message]: {request.message}"`，会污染原始指令 |

### 4.4 性能问题

| 编号 | 问题 | 影响 | 建议 |
|:---|:---|:---:|:---|
| **P-001** | `sync_engine.py` 每 5 分钟轮询所有进行中的子任务 | 中 | 子任务数量增长后，每次轮询的 API 调用数线性增长。建议改为 WebSocket 推送或增量轮询 |
| **P-002** | `agent_provisioner.py` 每次调用 `_load_skills_for_role` 都创建新的 `SkillLoader` 实例 | 低 | 虽然 SkillLoader 有内部缓存，但重复创建实例浪费资源。建议复用单例 |
| **P-003** | `template_loader.py` 中 `time.sleep(0.5)` 阻塞 Watchdog 线程 | 低 | 防抖动处理中的 sleep 会阻塞文件监控线程，如果多个文件同时变更可能丢失事件 |
| **P-004** | `DAG 快照` 在 `create_task` 中从 Redis 读取整个模板再提取 tasks | 低 | 模板较大时（如 50+ 节点），序列化/反序列化开销明显。建议只缓存 tasks 部分 |

### 4.5 安全隐患

| 编号 | 问题 | 严重性 | 建议 |
|:---|:---|:---:|:---|
| **S-001** | CORS 配置 `allow_origins=["*"]` | P1 | 生产环境应限制为特定域名 |
| **S-002** | `importlib` 动态导入任意路径的 `loader.py` | P1 | 如果 `skills_dir` 被恶意配置，可能加载恶意代码。应限制在预定义目录内 |
| **S-003** | Token 以环境变量明文存储 | P2 | 建议使用密钥管理服务（如 Vault） |
| **S-004** | Docker Exec 调用未做输入验证 | P1 | `agent_name`、`content` 等参数直接拼接到 CLI 命令中，存在命令注入风险。应做转义或白名单验证 |
| **S-005** | `complete_sub_task` API 无鉴权 | P1 | 任何知道 sub_task_id 的人都可以标记任务完成，应添加 Agent Key 验证 |

## 7. P0/P1/P2 问题清单

| 编号 | 严重性 | 问题描述 | 修复建议 |
|:---|:---:|:---|:---|
| **ARCH-001** | P0 | `complete_sub_task` API 无鉴权，任何知道 sub_task_id 的人都可以标记任务完成 | 添加 Agent Key 验证，或要求调用方提供会话 ID 与子任务记录匹配 |
| **ARCH-002** | P0 | Docker Exec CLI 调用未做输入验证，存在命令注入风险 | 对 `agent_name`、`content` 等参数做白名单验证或 Shell 转义，或使用 `shlex.quote()` |
| **ARCH-003** | P0 | DAG 快照中 `task_id` 与子任务记录 `id` 不匹配，`_unlock_dependent_tasks` 中的依赖检查逻辑可能失效 | 统一使用 `task_id` 或 `id`，在 SyncEngine 中建立映射关系 |
| **ARCH-004** | P1 | `complete_sub_task` 中 instruction 字段被追加完成消息，污染原始指令 | 新增 `completion_message` 字段存储完成消息，不要修改 instruction |
| **ARCH-005** | P1 | CORS 配置 `allow_origins=["*"]`，生产环境不安全 | 改为从环境变量读取允许的域名列表 |
| **ARCH-006** | P1 | `importlib` 动态导入 `loader.py`，如果 skills 目录被恶意配置可能加载恶意代码 | 验证加载路径在 `SKILLS_DIR` 范围内，使用 `Path.resolve().relative_to()` 检查 |
| **ARCH-007** | P1 | DAG 快照只保存了部分字段（task_id/name/type/dependencies/target_role），未保存 execution_context、output_definition 等 | 保存完整的 task 定义，或至少保存执行所需的关键字段 |
| **ARCH-008** | P1 | TC-E2E-004 测试响应显示 BUG-005/BUG-006 修复前的结果，需要重新验证修复后的 API | 重新执行 TC-E2E-004 测试，确认 `input_params` 和 `dag_snapshot` 字段已正确返回 |
| **ARCH-009** | P2 | `dev-breakdown` 节点缺少 `acceptance_criteria` | 添加动态任务分解的验收标准，如"输出合法 JSON 数组"、"每个子任务有 name/role/instruction" |
| **ARCH-010** | P2 | `get_prompt` 返回通用默认 prompt 而非角色专属 prompt | 配置 OpenMOSS 管理员 token 或提供各角色的默认 prompt 文件 |
| **ARCH-011** | P2 | SyncEngine 轮询间隔 5 分钟，任务完成到后续任务派发的延迟较高 | 考虑缩短轮询间隔或改为事件驱动 |
| **ARCH-012** | P2 | `template_loader.py` 中 `time.sleep(0.5)` 阻塞 Watchdog 线程 | 改用异步延迟或在线程池中使用 sleep |

## 8. 评审结论

**有条件通过**

### 理由：

**通过方面**：
1. 系统架构设计合理，Backend/OpenMOSS/OpenClaw 三层职责清晰
2. 核心模块（TemplateLoader、AgentProvisioner、Dispatcher、SyncEngine）实现与文档基本一致
3. 推拉结合的派发机制设计合理，有完善的 fallback
4. DAG 循环依赖检测、JSON Schema 校验等关键功能已实现
5. 已发现的 6 个 Bug 均已修复（代码层面）

**有条件的原因**：
1. **P0 安全问题未解决**：`complete_sub_task` API 无鉴权、Docker Exec 命令注入风险
2. **P0 数据一致性问题**：DAG 快照中 `task_id` 与子任务 `id` 不匹配可能导致依赖解锁逻辑失效
3. **测试验证不完整**：TC-E2E-004 的测试响应是 Bug 修复前的快照，需要重新执行验证
4. **DAG 快照不完整**：只保存了部分字段，与文档"完整 DAG 快照"描述不符

### 放行条件：
1. 修复 ARCH-001（complete_sub_task 鉴权）和 ARCH-002（命令注入）两个 P0 安全问题
2. 修复 ARCH-003（DAG 快照 ID 不匹配）问题
3. 重新执行 TC-E2E-004 测试，确认 BUG-005/BUG-006 修复生效
4. 补充 ARCH-007（DAG 快照完整性）的修复方案
