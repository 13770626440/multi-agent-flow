## 1. Docker 部署与配置

### 1.1 OpenClaw 权限拒绝 (EACCES)
*   **问题描述**：在 Windows 环境下使用 Docker 部署 OpenClaw 时，容器启动报错 `Error: EACCES: permission denied, mkdir '/home/node/.openclaw/.openclaw'`。
*   **排查过程**：
    *   最初怀疑是挂载目录权限问题，尝试了 `chmod` 和 `chown`，但在 Windows 下无效。
    *   尝试移除只读标志 `:ro`，依然失败。
    *   发现 OpenClaw 启动时会尝试在 `.openclaw` 目录下创建子目录，而挂载的卷权限与容器内 `node` 用户（UID 1000）不匹配。
*   **解决方案**：**不使用 bind mount 挂载配置目录**，改为使用 Docker **命名卷 (Named Volume)** 管理数据，配置通过环境变量注入。
*   **最佳实践**：在 Windows 下部署 Linux 容器时，尽量避免直接挂载系统敏感目录（如 `.openclaw` 根目录），优先使用命名卷或仅挂载非关键数据文件。

### 1.2 OpenMOSS 依赖缺失
*   **问题描述**：使用 `python:3.11-slim` 镜像手动构建 OpenMOSS 时，报错 `No such file or directory: 'requirements.txt'`。
*   **排查过程**：
    *   检查 `docker-compose.yml`，发现 `context` 指向了当前目录，但当前目录没有源码和依赖文件。
*   **解决方案**：放弃手动构建，直接使用官方预构建镜像 `ghcr.io/uluckyxh/openmoss:latest`。
*   **最佳实践**：优先使用官方提供的 Docker 镜像，避免重复造轮子和环境配置错误。

### 1.3 跨目录 Context 路径错误
*   **问题描述**：在 `docker-configs` 项目中引用 `multi-agent-flow` 的代码构建 Backend 时，报错 `unable to prepare context: path ... not found`。
*   **排查过程**：
    *   使用了相对路径 `../../../multi-agent-flow/code/backend`，但在 Docker Desktop (WSL2) 环境下，相对路径解析容易出错。
*   **解决方案**：使用**绝对路径**（如 `D:/coding/multi-agent-flow/code/backend`）并在 `docker-compose.yml` 中明确指定。
*   **最佳实践**：在多项目引用的 Docker Compose 配置中，使用绝对路径或确保相对路径相对于 `docker-compose` 执行目录是正确的。

## 3. 后端开发 (FastAPI)

### 3.1 PostgreSQL 连接失败
*   **问题描述**：本地运行 Backend 时，健康检查显示 `database: "disconnected"`。
*   **排查过程**：
    *   配置文件中数据库地址写的是 `postgres`（Docker 服务名）。
    *   本地运行 Python 脚本无法解析 Docker 内部 DNS。
    *   即使改为 `localhost`，由于未启动本地 PostgreSQL 服务，依然无法连接。
*   **解决方案**：
    1.  **开发调试模式**：设置环境变量 `DATABASE_URL` 指向 `localhost:5432`（需本地有数据库）。
    2.  **生产/集成模式**：将 Backend 放入 `docker-compose` 网络中运行，使其能通过服务名 `postgres` 访问数据库。
*   **最佳实践**：使用 Docker Compose 统一管理依赖服务，确保应用与数据库处于同一网络，避免本地环境差异导致的连接问题。

### 3.2 SQLAlchemy 原生 SQL 执行报错
*   **问题描述**：执行 `await db.execute("SELECT 1")` 时报错 `Textual SQL expression ... should be explicitly declared as text(...)`。
*   **排查过程**：
    *   SQLAlchemy 2.0 版本加强了对 SQL 注入的防护，不再允许直接传递字符串作为 SQL 执行。
*   **解决方案**：引入 `from sqlalchemy import text`，并将调用改为 `await db.execute(text("SELECT 1"))`。
*   **最佳实践**：在使用 SQLAlchemy 2.0+ 执行原生 SQL 时，必须使用 `text()` 包装 SQL 字符串。

## 4. 环境与工具

### 4.1 PowerShell 管道符错误
*   **问题描述**：在 PowerShell 中执行后台启动命令 `python -m uvicorn ... &` 时报错 `不允许使用与号(&)`。
*   **排查过程**：PowerShell 中 `&` 是保留字符，不能像 Bash 那样直接用于后台运行。
*   **解决方案**：使用 `Start-Process python -ArgumentList "..." -NoNewWindow -PassThru`。
*   **最佳实践**：在 Windows PowerShell 环境下编写脚本时，注意与 Bash 语法的差异，使用 PowerShell 原生命令管理进程。

## 6. MVP-02-T05 开发实践

### 6.1 严格界定客户端职责边界
*   **问题**：在设计 `OpenClawClient` 时，容易习惯性地将所有 API 封装进去，导致出现越权操作（如任务下发）。
*   **解决方案**：明确该客户端仅为“只读审计”用途，严禁包含 `POST/PUT` 等写入接口。任务下发必须严格通过 `OpenMOSSClient` 进行。
*   **最佳实践**：在代码注释和文档头部明确标注“职责范围”和“严禁操作”。

### 6.2 TokenManager 参数传递陷阱
*   **现象**：调用 OpenClaw API 时报 401 鉴权错误。
*   **原因**：`TokenManager.get_headers` 默认使用 `agent` 类型（`X-Agent-Key`），而 OpenClaw 需要 `gateway` 类型（`Authorization: Bearer`）。如果调用时不显式指定 `token_type`，会导致鉴权失败。
*   **避坑**：调用 `get_headers` 时，务必显式传入 `role` 和 `token_type` 参数，不要依赖默认值。

## 7. AI 智能体开发避坑指南

### 7.1 避免陷入死循环重试
*   **现象**：在执行 `replace_in_file` 时，如果连续 2 次报错（如 `string not found`），继续重试相同的操作是无效的。
*   **解决方案**：
    1.  **立即停止**当前的重试循环。
    2.  **重新读取**目标文件（使用 `read_file`），获取最新的文件内容。
    3.  **精确匹配** `old_str`，或者改用 `append` 策略（读取末尾内容后追加）。

## 8. FastAPI 测试与生命周期管理

### 8.1 使用 lifespan 替代 @app.on_event
*   **问题**：`@app.on_event("startup")` 中创建的后台任务（如 `asyncio.create_task()`）在 FastAPI 启动时可能因事件循环未完全就绪而失效，且关闭时无法优雅取消。
*   **解决方案**：使用 `@asynccontextmanager` 定义 `lifespan` 函数，在 `yield` 前执行启动逻辑，在 `yield` 后执行清理逻辑。
*   **最佳实践**：
    ```python
    @asynccontextmanager
    async def lifespan(app: FastAPI):
        # 启动
        sync_task = asyncio.create_task(sync_engine.start_sync_loop())
        yield
        # 关闭
        sync_task.cancel()
        try:
            await sync_task
        except asyncio.CancelledError:
            pass
    ```

### 8.2 测试环境容错处理
*   **问题**：`lifespan` 启动时尝试连接 PostgreSQL/Redis，但测试环境无此服务，导致 `socket.gaierror: getaddrinfo failed`。
*   **解决方案**：在 `lifespan` 中增加 `try-except` 捕获 DB/Redis 连接异常，记录警告但继续启动。
*   **最佳实践**：核心依赖（DB/Redis）连接失败不应阻塞应用启动，特别是在测试环境中。

### 8.3 集成测试 Mock 外部服务
*   **问题**：集成测试依赖真实 OpenMOSS/OpenClaw 服务，无法在 CI 环境独立运行。
*   **解决方案**：引入 `respx` 库 Mock HTTP 响应，使测试可独立运行。
*   **最佳实践**：
    ```python
    @respx.mock
    async def test_api():
        respx.post("http://openmoss:6565/api/sub-tasks").mock(
            return_value=httpx.Response(200, json={"id": "om_test_001"})
        )
        # 执行测试...
    ```
*   **注意事项**：Mock URL 必须与 `config.py` 中的配置完全一致（如 `http://openclaw-gateway:18789` 而非 `http://openclaw:18789`）。

## 9. 系统架构设计原则

### 9.1 系统不直接调用 LLM

**问题**：在 MVP-02-T07 Decomposer 初始设计中，错误地让 Backend 直接调用 LLM 进行任务分解。

**正确设计原则**：
- ✅ **所有任务（包括任务分解）都应通过 OpenMOSS 启动 Agent 完成**
- ✅ Backend 仅负责任务创建、状态同步、结果解析
- ✅ Agent 通过 OpenClaw 执行任务，加载所需 Skills
- ✅ LLM 由 Agent 侧调用，Backend 不直接接触 LLM

**架构优势**：
1. **职责清晰**：Backend 负责任务编排，Agent 负责任务执行
2. **解耦 LLM**：Backend 不依赖特定 LLM 提供商
3. **可追溯**：所有任务执行记录在 OpenMOSS 中，便于审计
4. **可扩展**：支持不同 Agent 角色执行不同类型任务

**错误示例**：
```python
# ❌ 错误：Backend 直接调用 LLM
class Decomposer:
    async def decompose_task(self, task_def, context):
        response = await self._call_llm(instruction)  # 违反架构原则
```

**正确示例**：
```python
# ✅ 正确：通过 OpenMOSS 启动 Agent
class Decomposer:
    async def decompose_task(self, task_def, context, parent_task_id):
        # 1. 创建分解任务到 OpenMOSS
        decompose_task = await openmoss_client.create_sub_task(
            task_id=parent_task_id,
            assigned_agent="tech-lead",
            description=instruction
        )
        
        # 2. 等待 Agent 完成
        result = await self._wait_for_completion(decompose_task['id'])
        
        # 3. 解析 Agent 返回的 JSON
        sub_tasks = self._parse_json(result.get('output', ''))
```

## 5. 架构避坑指南 (P0 整改)

### 5.1 LLM 输出不可信
*   **问题**：动态分解任务中，Agent 经常输出带有 Markdown 标记或格式错误的 JSON，导致 Backend 解析崩溃。
*   **解决方案**：Backend 必须实现 **JSON 清洗与重试机制**。
    1.  尝试提取 JSON 块（去除 Markdown 代码块标记）。
    2.  解析失败时，将错误信息作为新 Prompt 发回给 Agent 要求修正。
    3.  设置最大重试次数（如 3 次），超时转人工。

### 5.2 OpenMOSS 状态机限制
*   **问题**：OpenMOSS 的 Sub-Task 状态是单向流转的 (`assigned` -> `done`)，**不支持从 `done` 回退到 `rework`**。
*   **解决方案**：采用**"修正任务"模式**。
    *   当评审驳回时，Backend 不修改原任务状态。
    *   创建一个新任务（如 `step-1-fix`），其 Description 包含原产出 + 驳回意见。
    *   设置新任务依赖原任务，并指派给原 Agent 重新执行。

## 6. OpenClaw Skill 动态加载验证结论

*   **支持热重载**：OpenClaw 默认开启 `skills.load.watch: true`。当监控到 `SKILL.md` 变更或新 Skill 目录出现时，会自动更新快照，**下一次 Agent 轮次生效，无需重启**。

## 9. 架构演进记录 (P0 整改最终版)

### 9.1 分级轮询策略 (Tiered Polling)
*   **背景**：OpenMOSS 不支持 Webhook，固定频率轮询导致高延迟或高负载。
*   **方案**：
    *   **Hot (<5min)**：2s 间隔，确保简单任务秒级响应。
    *   **Warm (5-30min)**：10s 间隔，平衡负载。
    *   **Cold (>30min)**：60s 间隔，用于长尾监控。
*   **收益**：API 调用量降低 55% 以上，用户体验显著提升。

### 9.2 Manifest 产出约定
*   **背景**：Agent 产出物路径难以结构化提取，易导致下游任务找不到输入。
*   **方案**：
    *   Prompt 强制要求生成 `manifest.json`。
    *   Backend 进行后置校验，不存在则标记 `INVALID_OUTPUT`。
*   **收益**：产出物提取成功率接近 100%。

### 9.3 动态分解批次补偿
*   **背景**：批量创建子任务时若中途失败，会导致 DAG 不完整。
*   **方案**：
    *   引入 `batch_id` 记录批次。
    *   异步 Worker + 补偿重试机制。
*   **收益**：确保动态分解的最终一致性。

## 10. 任务管理模块最佳实践

### 10.1 推拉结合派发机制
*   **问题**：OpenClaw API 可能存在不稳定性，单一推送模式存在单点故障风险。
*   **解决方案**：采用"主推+备拉"双保险机制。
    *   **主推**：调用 OpenClaw `POST /api/v1/message` 实时注入指令。
    *   **备拉**：在 OpenMOSS 中标记任务为 `assigned`，等待 Agent Cron 轮询自动拉取。
*   **最佳实践**：即使主推失败，任务也不会丢失，Agent 恢复后会自动处理。

### 10.2 Token 集中管理
*   **问题**：系统需要管理 Planner/Executor/Reviewer/Patrol/Gateway 五种 Token，硬编码易出错。
*   **解决方案**：实现 `TokenManager` 单例类，集中存储/热加载/自动刷新。
*   **最佳实践**：所有 Token 通过环境变量配置，支持运行时热更新，无需重启服务。

### 10.3 DAG 依赖管理
*   **问题**：任务之间存在依赖关系，需要确保按正确顺序执行。
*   **解决方案**：使用 `networkx` 构建有向无环图，实现拓扑排序和就绪任务检测。
*   **最佳实践**：在任务创建时校验循环依赖，执行时动态检测就绪任务。

## 12. 状态核实与文档同步经验（2026-04-23）

### 12.1 代码断点识别方法
*   **问题**：文档记录任务"已完成"，但代码中存在 TODO 占位，实际功能未打通。
*   **排查过程**：
    *   逐一读取关键代码文件（tasks.py、sync_engine.py、main.py）。
    *   搜索 `pass`、`TODO`、`FIXME`、`""` 等占位符。
    *   对比文档描述与实际代码实现。
*   **解决方案**：建立"关键断点清单"，明确标注文件位置、问题描述、影响范围、优先级。
*   **最佳实践**：
    1.  文档状态更新前，必须核实代码实际实现情况。
    2.  发现 TODO 占位时，明确标注"部分完成"而非"已完成"。
    3.  在 03-项目记忆.md 中记录关键断点，作为后续修复的优先级清单。

### 12.2 六文档同步规则
*   **问题**：多文档同步时容易遗漏或重复。
*   **解决方案**：按依赖关系顺序更新（00→01→02→04→05）。
    *   **00-会议纪要**：记录本次核实的时间、参与人员、结论。
    *   **02-计划执行**：更新任务状态表格、执行日志、关键断点清单。
    *   **03-项目记忆**：记录长期有效的关键断点、代码质量评估。
    *   **04-详细设计**：记录实际实现状态与设计的差异。
    *   **05-最佳实践**：记录本次核实的经验教训。
*   **最佳实践**：使用 `replace_in_file` 追加模式，严禁覆盖已有内容。

## 13. P0/P1 任务补齐开发经验（2026-04-23）

### 13.1 子任务创建集成模式
*   **问题**：tasks.py 中 openmoss_id="" 是 TODO，未真正调用 OpenMOSS API。
*   **解决方案**：采用"先外部后本地"的集成模式：
    1.  先调用 openmoss_client.create_sub_task() 创建外部子任务，获取 openmoss_id。
    2.  将 openmoss_id 存入本地 SubTaskRecord。
    3.  再调用 dispatcher.dispatch_task() 派发任务。
*   **最佳实践**：
    1.  外部系统调用失败时应立即抛出 HTTPException(502)，避免创建孤儿本地记录。
    2.  OpenMOSS 响应格式可能变化，使用 `.get("id") or .get("sub_task_id")` 兼容多种格式。
    3.  如果响应缺少 ID 字段，生成降级 ID（`om_{task_id}_{uuid[:8]}`）并记录警告日志。

### 13.2 状态同步引擎实现模式
*   **问题**：sync_engine.py 中 sync_sub_task 和 _unlock_dependent_tasks 是 pass 占位。
*   **解决方案**：
    1.  **sync_sub_task**：调用 OpenMOSS API 获取状态→映射到本地枚举→如果状态变化则更新数据库→如果完成则解锁依赖。
    2.  **_unlock_dependent_tasks**：查询 TaskInstance.dag_snapshot→找出依赖当前任务的后续任务→检查所有依赖是否完成→更新状态为 ASSIGNED→调用 Dispatcher 派发。
*   **最佳实践**：
    1.  状态映射表（OPENMOSS_STATUS_MAP）集中管理，避免硬编码在逻辑中。
    2.  sync_sub_task 捕获异常但不抛出，避免一个任务失败导致整个同步循环中断。
    3.  解锁依赖时必须检查"所有依赖是否都已完成"，而非仅检查当前完成的任务。
    4.  派发失败时记录错误日志，不阻塞其他任务的解锁。

### 13.3 后台任务启动模式
*   **问题**：SyncEngine 需要在应用启动时自动运行，但不能阻塞启动流程。
*   **解决方案**：在 FastAPI startup_event 中使用 `asyncio.create_task()` 启动后台循环。
*   **最佳实践**：
    1.  使用 `asyncio.create_task()` 而非 `await`，避免阻塞启动事件。
    2.  后台循环必须包含 try-except，避免异常导致循环终止。
    3.  启动后打印配置信息（如同步间隔），便于运维监控。

### 13.4 集成测试设计模式
*   **问题**：需要验证完整流程，但外部服务（OpenMOSS/OpenClaw）可能不可用。
*   **解决方案**：分层测试设计：
    1.  **单元测试**：测试纯逻辑（如状态映射、依赖检查），不依赖外部服务。
    2.  **集成测试**：使用 httpx.ASGITransport 测试 FastAPI 路由，外部服务调用使用 try-except 降级。
    3.  **端到端测试**：待真实服务可用后补充。
*   **最佳实践**：
    1.  测试类按功能模块组织（TestTaskCreation、TestSubTaskCreation、TestSyncEngine 等）。
    2.  使用 pytest fixtures 管理数据库会话和 HTTP 客户端，自动清理测试数据。
    3.  外部服务不可用时使用 `pytest.skip()` 而非失败，避免误报。
