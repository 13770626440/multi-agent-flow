## 1. Docker 部署与配置

### 1.1 OpenClaw 权限拒绝 (EACCES)
*   **问题描述**：在 Windows 环境下使用 Docker 部署 OpenClaw 时，容器启动报错 `Error: EACCES: permission denied, mkdir '/home/node/.openclaw/.openclaw'`。
*   **排查过程**：
    *   最初怀疑是挂载目录权限问题，尝试了 `chmod` 和 `chown`，但在 Windows 下无效。
    *   尝试移除只读标志 `:ro`，依然失败。
    *   发现 OpenClaw 启动时会尝试在 `.openclaw` 目录下创建子目录，而挂载的卷权限与容器内 `node` 用户（UID 1000）不匹配。
*   **解决方案**：**不使用 bind mount 挂载配置目录**，改为使用 Docker **命名卷 (Named Volume)** 管理数据，配置通过环境变量注入。
*   **最佳实践**：在 Windows 下部署 Linux 容器时，尽量避免直接挂载系统敏感目录（如 `.openclaw` 根目录），优先使用命名卷或仅挂载非关键数据文件。

### 1.2 OpenMOSS 依赖缺失
*   **问题描述**：使用 `python:3.11-slim` 镜像手动构建 OpenMOSS 时，报错 `No such file or directory: 'requirements.txt'`。
*   **排查过程**：
    *   检查 `docker-compose.yml`，发现 `context` 指向了当前目录，但当前目录没有源码和依赖文件。
*   **解决方案**：放弃手动构建，直接使用官方预构建镜像 `ghcr.io/uluckyxh/openmoss:latest`。
*   **最佳实践**：优先使用官方提供的 Docker 镜像，避免重复造轮子和环境配置错误。

### 1.3 跨目录 Context 路径错误
*   **问题描述**：在 `docker-configs` 项目中引用 `multi-agent-flow` 的代码构建 Backend 时，报错 `unable to prepare context: path ... not found`。
*   **排查过程**：
    *   使用了相对路径 `../../../multi-agent-flow/code/backend`，但在 Docker Desktop (WSL2) 环境下，相对路径解析容易出错。
*   **解决方案**：使用**绝对路径**（如 `D:/coding/multi-agent-flow/code/backend`）并在 `docker-compose.yml` 中明确指定。
*   **最佳实践**：在多项目引用的 Docker Compose 配置中，使用绝对路径或确保相对路径相对于 `docker-compose` 执行目录是正确的。

## 2. OpenMOSS Docker 部署指南 (SOP)

> **适用场景**：需要独立部署或集成 OpenMOSS 任务调度中间件时。

### 2.1 核心配置
*   **镜像**：`ghcr.io/uluckyxh/openmoss:latest` (官方预构建)
*   **端口**：`6565` (默认)
*   **网络**：需与 OpenClaw 和 Backend 处于同一 Docker 网络 (如 `maf-net`)

### 2.2 目录结构准备
```text
openmoss-deploy/
├── data/                 # 数据库文件 (SQLite)
├── docker-data/
│   ├── config/           # 配置文件
│   │   └── config.yaml
│   └── static/           # WebUI 静态资源 (自动下载)
└── docker-compose.yml
```

### 2.3 `config.yaml` 核心配置
```yaml
project:
  name: "MAF-OpenMOSS"

admin:
  password: "admin123" # 首次启动后自动哈希

agent:
  registration_token: "your-secret-token" # Agent 注册必须
  allow_registration: true

server:
  port: 6565
  host: "0.0.0.0"
  external_url: "" # 若有公网 IP 需填写

database:
  type: sqlite
  path: "./data/tasks.db"

workspace:
  root: "/workspace"
```

### 2.4 `docker-compose.yml` 配置片段
```yaml
services:
  openmoss:
    image: ghcr.io/uluckyxh/openmoss:latest
    container_name: maf-openmoss
    restart: unless-stopped
    ports:
      - "6565:6565"
    environment:
      OPENMOSS_CONFIG: /data/config/config.yaml
    volumes:
      - ./data:/app/data
      - ./docker-data/config:/data/config
      - ./docker-data/static:/app/static
    networks:
      - maf-net
    healthcheck:
      test: ["CMD", "curl", "-f", "http://127.0.0.1:6565/api/health"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 60s
```

### 2.5 常见问题排查
*   **启动失败**：检查 `config.yaml` 路径是否正确映射到 `/data/config/config.yaml`。
*   **WebUI 无法加载**：确保容器能访问外网（首次启动需从 GitHub 下载前端资源）。
*   **Agent 注册失败**：检查 `registration_token` 是否与请求 Header 一致。

## 3. 后端开发 (FastAPI)

### 3.1 PostgreSQL 连接失败
*   **问题描述**：本地运行 Backend 时，健康检查显示 `database: "disconnected"`。
*   **排查过程**：
    *   配置文件中数据库地址写的是 `postgres`（Docker 服务名）。
    *   本地运行 Python 脚本无法解析 Docker 内部 DNS。
    *   即使改为 `localhost`，由于未启动本地 PostgreSQL 服务，依然无法连接。
*   **解决方案**：
    1.  **开发调试模式**：设置环境变量 `DATABASE_URL` 指向 `localhost:5432`（需本地有数据库）。
    2.  **生产/集成模式**：将 Backend 放入 `docker-compose` 网络中运行，使其能通过服务名 `postgres` 访问数据库。
*   **最佳实践**：使用 Docker Compose 统一管理依赖服务，确保应用与数据库处于同一网络，避免本地环境差异导致的连接问题。

### 3.2 SQLAlchemy 原生 SQL 执行报错
*   **问题描述**：执行 `await db.execute("SELECT 1")` 时报错 `Textual SQL expression ... should be explicitly declared as text(...)`。
*   **排查过程**：
    *   SQLAlchemy 2.0 版本加强了对 SQL 注入的防护，不再允许直接传递字符串作为 SQL 执行。
*   **解决方案**：引入 `from sqlalchemy import text`，并将调用改为 `await db.execute(text("SELECT 1"))`。
*   **最佳实践**：在使用 SQLAlchemy 2.0+ 执行原生 SQL 时，必须使用 `text()` 包装 SQL 字符串。

## 4. 环境与工具

### 4.1 PowerShell 管道符错误
*   **问题描述**：在 PowerShell 中执行后台启动命令 `python -m uvicorn ... &` 时报错 `不允许使用与号(&)`。
*   **排查过程**：PowerShell 中 `&` 是保留字符，不能像 Bash 那样直接用于后台运行。
*   **解决方案**：使用 `Start-Process python -ArgumentList "..." -NoNewWindow -PassThru`。
*   **最佳实践**：在 Windows PowerShell 环境下编写脚本时，注意与 Bash 语法的差异，使用 PowerShell 原生命令管理进程。

## 5. 架构避坑指南 (P0 整改)

### 5.1 LLM 输出不可信
*   **问题**：动态分解任务中，Agent 经常输出带有 Markdown 标记或格式错误的 JSON，导致 Backend 解析崩溃。
*   **解决方案**：Backend 必须实现 **JSON 清洗与重试机制**。
    1.  尝试提取 JSON 块（去除 Markdown 代码块标记）。
    2.  解析失败时，将错误信息作为新 Prompt 发回给 Agent 要求修正。
    3.  设置最大重试次数（如 3 次），超时转人工。

### 5.2 OpenMOSS 状态机限制
*   **问题**：OpenMOSS 的 Sub-Task 状态是单向流转的 (`assigned` -> `done`)，**不支持从 `done` 回退到 `rework`**。
*   **解决方案**：采用**"修正任务"模式**。
    *   当评审驳回时，Backend 不修改原任务状态。
    *   创建一个新任务（如 `step-1-fix`），其 Description 包含原产出 + 驳回意见。
    *   设置新任务依赖原任务，并指派给原 Agent 重新执行。

## 6. OpenClaw Skill 动态加载验证结论

### 6.1 核心发现
*   **支持热重载**：OpenClaw 默认开启 `skills.load.watch: true`。当监控到 `SKILL.md` 变更或新 Skill 目录出现时，会自动更新快照，**下一次 Agent 轮次生效，无需重启**。
*   **目录优先级**：`<workspace>/skills` > `~/.agents/skills` > `~/.openclaw/skills`。
*   **门控机制**：Skill 可通过 `metadata.openclaw` 定义加载条件（如 `requires.bins`, `os` 等）。

### 6.2 验证结论
*   **方案可行**：利用 OpenClaw 的热重载机制，Backend 或 `agency-agent` 可以在运行时动态放置 Skill 文件，Agent 能够自动识别并加载。
*   **最佳实践**：建议将所有标准 Skill 预装在 `~/.openclaw/skills`，并通过 `agency-agent` 控制加载上下文，而非频繁读写文件系统，以提高稳定性。

## 7. 文件共享与路径引用

*   **问题**：不同 Agent 容器间文件系统隔离，传递路径无效。
*   **解决方案**：采用 **Docker Shared Volume (`/workspace`)**。
    *   所有 Agent 容器挂载同一共享卷。
    *   YAML 中通过 `input_mapping` 传递绝对路径（如 `/workspace/task-1/output.csv`）。

## 9. 架构演进记录 (P0 整改最终版)

### 9.1 分级轮询策略 (Tiered Polling)
*   **背景**：OpenMOSS 不支持 Webhook，固定频率轮询导致高延迟或高负载。
*   **方案**：
    *   **Hot (<5min)**：2s 间隔，确保简单任务秒级响应。
    *   **Warm (5-30min)**：10s 间隔，平衡负载。
    *   **Cold (>30min)**：60s 间隔，用于长尾监控。
*   **收益**：API 调用量降低 55% 以上，用户体验显著提升。

### 9.2 Manifest 产出约定
*   **背景**：Agent 产出物路径难以结构化提取，易导致下游任务找不到输入。
*   **方案**：
    *   Prompt 强制要求生成 `manifest.json`。
    *   Backend 进行后置校验，不存在则标记 `INVALID_OUTPUT`。
*   **收益**：产出物提取成功率接近 100%。

### 9.3 动态分解批次补偿
*   **背景**：批量创建子任务时若中途失败，会导致 DAG 不完整。
*   **方案**：
    *   引入 `batch_id` 记录批次。
    *   异步 Worker + 补偿重试机制。
*   **收益**：确保动态分解的最终一致性。

## 10. 任务管理模块最佳实践

### 10.1 推拉结合派发机制
*   **问题**：OpenClaw API 可能存在不稳定性，单一推送模式存在单点故障风险。
*   **解决方案**：采用"主推+备拉"双保险机制。
    *   **主推**：调用 OpenClaw `POST /api/v1/message` 实时注入指令。
    *   **备拉**：在 OpenMOSS 中标记任务为 `assigned`，等待 Agent Cron 轮询自动拉取。
*   **最佳实践**：即使主推失败，任务也不会丢失，Agent 恢复后会自动处理。

### 10.2 Token 集中管理
*   **问题**：系统需要管理 Planner/Executor/Reviewer/Patrol/Gateway 五种 Token，硬编码易出错。
*   **解决方案**：实现 `TokenManager` 单例类，集中存储/热加载/自动刷新。
*   **最佳实践**：所有 Token 通过环境变量配置，支持运行时热更新，无需重启服务。

### 10.3 DAG 依赖管理
*   **问题**：任务之间存在依赖关系，需要确保按正确顺序执行。
*   **解决方案**：使用 `networkx` 构建有向无环图，实现拓扑排序和就绪任务检测。
*   **最佳实践**：在任务创建时校验循环依赖，执行时动态检测就绪任务。

### 5.1 核心发现
*   **角色绑定**：创建子任务时，通过 `assigned_agent` 字段指定 Agent ID，任务状态会自动变为 `assigned`，无需 Agent 手动 Claim。

*   **数据持久化**：OpenMOSS 数据库完整保存了任务上下文，支持 Backend 后续查询和 Reviewer 验收。
